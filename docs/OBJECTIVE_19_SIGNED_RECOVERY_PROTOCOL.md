# Objective 19 — signed, operator-led offline audit recovery

This is an **offline, single-host prototype**. It never accesses Shopify, checkout, orders, customers, or any hosted authentication. It does **not** supply an independent durable anchor or an operator signing service. The existing HMAC audit key and separate independent anchor remain mandatory. An operator must independently inspect trusted anchor records and the locally authenticated ledger before authorizing any repair.

## Exact failure window and policy

Objective 18 atomically renames `ledger.json`, then separately compare-and-sets an external anchor. If execution stops after rename but before anchor CAS, the ledger may be **exactly one committed sequence ahead** of the anchor. Normal reads and writes continue to fail closed with `LEDGER_AUDIT_ROLLBACK`. Never replace an old ledger, restore an old anchor, silently reset a sequence, or remove replay tombstones.

The new `recoverInterruptedAudit({authorization})` method is the **only** explicit recovery path. It first validates an independently signed, short-lived Ed25519 permit; obtains the filesystem transaction lock; parses and validates the full ledger; verifies its HMAC with a configured audit key; reads the independent anchor; and permits **only** `anchor sequence N → N+1` when the ledger has sequence `N+1`, its authenticated `previousMac` equals the anchor MAC, and the signed target matches the ledger's exact MAC. Genesis is `null → sequence 1` with all-zero previous MAC. A successful recovery updates **only** the independent anchor through its CAS contract; it does not edit ledger bytes. Readback must confirm the exact target. If already at the exact target, an otherwise valid signed permit returns `already-recovered` without another CAS. The normal read path then independently verifies the matching anchor.

## Independent authorization contract

Configure `audit.recovery = { ledgerId, publicKey }`, where `publicKey` is a **trusted Ed25519 public KeyObject** installed through a trusted channel and `ledgerId` is a unique stable, non-secret identifier for this ledger trust domain. **Never** supply a private key to the ledger adapter. Store the private signing key offline and independently of the machine holding the ledger and its HMAC keys. The recovery service/operator must verify the actual trusted anchor and evidence for the pending write **outside the local ledger** before signing. A signed permit alone proves authorization by that key, not that a human independently inspected evidence.

A permit has **exactly** these fields in the canonical signing order: `schema`, `ledgerId`, `authorizationId`, `issuedAt`, `expiresAt`, `expectedAnchor`, `targetAnchor`, `reason`, followed by `signature`. `schema` is `TJ-OFFLINE-LEDGER-RECOVERY-1`; `authorizationId` is a lowercase UUID; timestamps are integer Unix milliseconds; `expiresAt` is strictly future, `issuedAt` is not future, and validity lasts no longer than 15 minutes; `reason` is a trimmed, printable 8–200-character operator note. Anchors are `null` for genesis or exact `{sequence: positive safe integer, mac: 64 lowercase hex}` objects. The 64-byte Ed25519 signature is canonical unpadded base64url over the UTF-8 bytes `TJ-OFFLINE-LEDGER-RECOVERY-1` + NUL + `JSON.stringify(payload)`, where `payload` is an object constructed in the field order above, without `signature`. The signed target binds the entire audited ledger snapshot through its HMAC. This format is a narrow offline test contract, not a general production recovery protocol.

No permit may repair missing/corrupt/tampered ledger content, a missing historical HMAC key, a mismatched prior MAC, an anchor that is ahead or diverged, a gap larger than one, a wrong ledger identity, or unavailable anchor services. Signature verification and anchor CAS happen under different trust boundaries; **the configured public key must itself be trusted**. A compromised private key, HMAC key, or anchor invalidates the assumed guarantees. The signed permit is bounded by its target and prior anchor; successful reuse is an idempotent acknowledgement only. This prototype does not maintain an independent durable spent-authorization ledger.

## Test and release gates

Run `node --test tests/objective19-audit-recovery.test.mjs` and `npm test`. Tests generate disposable Ed25519 keys in memory and use a **volatile fake anchor**. They cover simulated process interruptions, signed operator authorization, replay/idempotency, concurrent recovery, forgery, expiration, wrong trust domain, anchor divergence/outages, tampering, corruption, genesis, and the fact that recovery does not rewrite the local ledger. These are synthetic offline fixtures, **not** a production audit, hosted security service, Shopify proof, or manufacturing authorization.
